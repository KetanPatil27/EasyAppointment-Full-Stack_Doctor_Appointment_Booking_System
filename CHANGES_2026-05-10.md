## ✨ New Features Added

### Per-email rate limiting on password reset
- **What it does:** Caps password-reset requests at 3 per email per hour. Blocks the 4th with a 429 error message.
- **Why it was needed:** The existing IP-level limiter could be bypassed by an attacker rotating IPs. Per-email throttling makes that pointless and also stops an honest mistake (typing the wrong email and spamming reset emails to a stranger).
- **Files affected:**
  - `backend/src/services/forgot-password/forgot-password.class.ts`
- **How to test:**
  1. POST `/forgot-password` with the same registered email 4 times in a row.
  2. First 3 succeed.
  3. 4th returns `429 TooManyRequests` with message "Too many reset attempts for this email…".
- **Status:** ✅ Done

### Configurable strict email validation on password reset
- **What it does:** Lets the operator decide whether `/forgot-password` returns "No account found" (better UX) or a generic message (better against email enumeration). Controlled by `STRICT_EMAIL_VALIDATION=true|false`.
- **Why it was needed:** Default of generic message is privacy-preserving but confusing for legit users with typos. Strict mode is more user-friendly when the threat model allows it.
- **Files affected:**
  - `backend/src/services/forgot-password/forgot-password.class.ts`
  - `frontend/app/forgot-password/page.tsx`
  - `backend/.env.example`
- **How to test:** Set the env var both ways, restart, and submit a non-existent email. Frontend shows an amber "No account found" alert with a link to `/register` in strict mode; success banner in generic mode.
- **Status:** ✅ Done

### Admin moderation cascade — suspend / delete / restore with full notification chain
- **What it does:** When an admin suspends or deletes a user, a single transaction updates the user record, slot calendar, and future appointments together — then sends emails to the user themselves AND to every patient with a future appointment with that doctor. Includes a 30-day restore window and an append-only audit log.
- **Why it was needed:** The old hard-delete cascade was non-atomic and nobody got notified. Patients with upcoming bookings were left in the dark; data could end up inconsistent if any step failed; and there was no way to roll back an accidental suspension.
- **Files affected:**

  - `backend/src/services/doctors/doctors.hook.ts` (hide deleted/suspended from public listings)
  - `backend/src/services/audit-logs/*` (new — append-only collection, admin-readable)
  - `backend/src/services/restore-user/*` (new — admin restore within 30 days)
  - `backend/src/utils/cascade-suspend-delete.ts` (new — transactional orchestrator)
  - `backend/src/utils/notification-emails.ts` (new — HTML templates)
  - `backend/src/utils/mailer.ts` (`sendNotificationEmail` wrapper)
  - `backend/src/mongodb.ts` (expose `mongoClient` for `.startSession()`)
  - `backend/src/services/index.ts` (register new services)

- **How to test:**

Verify: user.status='suspended', all slots flipped to `status='inactive'`, future appts cancelled with `cancellationReason='doctor_suspended'`, audit log entry created. Doctor receives suspension email; every patient with a future booking receives a cascade email with alternative-doctor suggestions.
  2. Unsuspend → slots reactivate; cancelled appts stay cancelled (those patients already moved on).
  3. Delete → soft delete (`isDeleted=true`), slots `status='deleted'`, future appts cancelled with `doctor_removed`, `refundFlagged=true`. Doctor + patients emailed.

  5. Within 30 days: POST `/restore-user { userId, reason }` → user back, slots reactivated.
  6. Past 30 days (manually backdate `deletedAt`): restore returns 400.
  7. Non-admin tries `/restore-user` → 403.

## 🐛 Bugs Fixed

### Doctor availability — slot isolation broken (every doctor saw everyone's slots)
- **Problem:** When a doctor opened the "Manage Availability" page, they saw the calendar of every other doctor in the system. Each doctor must only see their own.
- **Root cause:** The slots service used a custom `optionalAuth` hook that authenticated only if `headers.authorization` was present. After Phase 1 we moved JWT to httpOnly cookies, so no doctor request had the `Authorization` header anymore. Result: `params.user` was always undefined → `filterSlotsByDoctor` did nothing → every doctor's slots came back unfiltered.
- **Solution:** Replaced `optionalAuth` with `tryAuthenticate` that calls `authenticate('jwt')` and **swallows failures**. The JWT strategy reads from cookie OR header (Phase 1's `CustomJWTStrategy.parse`), so cookie-only requests now authenticate cleanly. Anonymous browsing still works because failed auth just falls through. Defense-in-depth at three layers:
  1. Backend hook authenticates and force-overwrites `query.doctorId` to the logged-in doctor's `_id`.
  2. MongoDB query field is explicitly `doctorId`.
  3. Frontend now passes `?doctorId=<currentUser._id>` for clarity (server overwrites anyway, but the explicit param surfaces bugs faster).
- **Files affected:**
  - `backend/src/services/slots/slots.hook.ts`
  - `frontend/services/appointmentService.ts` (`getMySlots(currentDoctorId?)`)
  - `frontend/app/doctor/availability/page.tsx`
- **Severity:** 🔴 Critical (data isolation / privacy leak)

### Reviews endpoint exposed all patients' reviews to anonymous queries
- **Problem:** Bonus fix discovered during Upgrade 2's audit. Anonymous `GET /reviews` with no `doctorId` filter returned every review of every doctor by every patient.
- **Root cause:** `filterByRole` hook returned early when no user was logged in, with no scoping fallback. Public review feed was unbounded.
- **Solution:** Anonymous queries now require a `doctorId` query param; missing it returns 400. Public doctor profile pages already pass it, so legitimate browsing is unaffected.
- **Files affected:**
  - `backend/src/services/reviews/reviews.hook.ts`
- **Severity:** 🟡 Medium (publicly displayed data, but unbounded scrape risk)

## 🔧 Improvements & Refactoring

- **Centralised error logging on email failures.** The cascade orchestrator and the existing appointment hook now emit structured error logs on email failure (with provider flags + SMTP code), so problems surface in Render logs without needing code-spelunking.
- **Auth audit across all services.** While fixing slots, audited every service hook for the same cookie-vs-header pattern. Verified `appointments`, `prescriptions`, `messages`, `health-data`, `patients` all use `authenticate('jwt')` directly (cookie-aware) — no other instances of the same bug.
- **Unified `cascadeSuspendOrDelete` orchestrator.** Replaced the previous ad-hoc hard-delete code with a single function that handles all three actions (suspend / unsuspend / delete) with consistent semantics, atomicity, and notification handling. One place to change the behaviour matrix instead of three.
- **Append-only audit log pattern.** `audit-logs` service blocks external `create` and all `remove` at the hook layer — admin can read the trail but never overwrite it.

## 📚 What I Learned Today

- **Cookie-based auth requires every hook on the auth path to be cookie-aware.** Pattern-matching on `headers.authorization` silently breaks the moment auth migrates to cookies. The lesson: `try { authenticate('jwt') } catch { …}` is more robust than `if (headers.authorization)`.
- **MongoDB transactions in the Node driver need access to the `MongoClient`, not just the `Db`.** The Db object alone can't `.startSession()`. Always expose the client on the app for code that needs atomic multi-collection writes.
- **OTPs should never live in the request/response body — only in the email channel.** The `_pendingOtp` stash on `context.params` keeps the plain code internal to the create flow; the response body has only the user record (with `otpHash` stripped via `protect`).
- **Idempotent migrations win.** The `specialization` migration's filter (`specializations` array missing or empty) means re-running after a partial deploy is safe — any second run finds nothing to do.
