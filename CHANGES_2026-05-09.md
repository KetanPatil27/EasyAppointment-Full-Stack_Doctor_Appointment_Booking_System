## 🐛 Bugs Fixed

### Custom domain blocked by CORS
- **Problem:** After attaching `easyappointment.online`, every API call from the new domain hit `CORS blocked request from origin: https://easyappointment.online` in backend logs.
- **Root cause:** The backend's `ALLOWED_ORIGINS` env var only contained the original `https://easyappointment-app.onrender.com`. CORS allowlist is exact-match, so the new domain was rejected.
- **Solution:** Updated `ALLOWED_ORIGINS` on Render to a JSON array containing both: `["https://easyappointment.online","https://easyappointment-app.onrender.com"]`. Saved → backend auto-redeployed → CORS warnings stopped.
- **Severity:** 🟠 High (frontend functional but unable to talk to backend)

### Reset-password email links pointed at `localhost:3000`
- **Problem:** Forgot-password flow worked end-to-end, email arrived, but the link in the email was `http://localhost:3000/reset-password?token=…` — useless for production users.
- **Root cause:** Backend mailer fell back to its dev default because `FRONTEND_URL` env var wasn't set on Render.
- **Solution:** Set `FRONTEND_URL=https://easyappointment.online` (no trailing slash) on the backend service. Auto-redeploy.
- **Severity:** 🟡 Medium

## 📚 What I Learned Today

- **Documentation has a half-life.** Writing `DEPLOYMENT.md` immediately after the marathon meant capturing the *misleading* symptoms (TLS error from missing allowlist, ETIMEDOUT from blocked SMTP) while they were still fresh. A week later those would have read like vague pattern-matching.
- **CORS exact-match is unforgiving.** Any difference between the env-var value and the browser's `Origin` header (trailing slash, http vs https, www vs non-www) blocks the request. Worth scripting a CI check that hits every production origin and asserts a 200.
- **Render's HTTPS for custom domains is automatic** — you only have to add a CNAME record and verify; no manual cert management. Easier than I expected.
